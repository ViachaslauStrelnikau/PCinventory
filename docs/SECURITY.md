# Firebase. Правила доступа и локальная проверка

Эти правила проверены в Auth и Firestore Emulator на синтетических данных проекта `demo-pcinventory`. Локальные проверки запускает CI. У Windows-агента есть режим отправки в локальный эмулятор. Развёртывание в облаке и подключение фронтенда относятся к следующим этапам.

## Роли и приём

| Роль | Разрешённые операции |
|---|---|
| `COLLECTOR` | Прочитать собственный документ роли. Создать `PENDING` в `inventoryReports/{reportId}`, пока открыт приём. |
| `ADMIN` | Читать реестр и входящие отчёты. Править, принимать и отклонять отчёты. Создавать, редактировать, архивировать и восстанавливать карточки, окончательно удалять карточки из архива. Управлять `settings/inventory.acceptingReports`. |
| `USER` | Читать собственную роль и реестр ПК. Статистика и выгрузки строятся на основе чтения карточек. |
| Пользователь без активной роли | Аутентифицированный пользователь может прочитать только собственный документ роли. |

Любая операция над отчётом, карточкой или переключателем приёма проверяет `users/{uid}` и `enabled` при запросе. Клиентские приложения не получают прав изменять роли. Учётная запись сборщика создаёт отчёт с ID из пути, своим UID и серверным временем. В отчёте обязательны здание, этаж и кабинет. Отсутствующий документ настройки, выключенный приём и отключённая роль блокируют новые отправки. Возобновление приёма требует явного действия администратора.

## Исправление, принятие и отклонение

Администратор сохраняет исправления ожидающего отчёта в `correction` с техническими и учётными данными, UID и серверным временем. Оригинал отчёта сохраняется. Исправленная версия сохраняется перед решением о принятии. После обработки отчёт и его исправления защищены от правок.

Принятие одной транзакцией переводит отчёт из `PENDING` в `ACCEPTED` и создаёт или обновляет `computers/{deviceId}`. Правила сверяют оба документа до и после записи. Карточка получает технические данные и местоположение из сохранённого исправления или исходного отчёта с указанием ID и времени отправки. При обновлении сохраняется текущий статус карточки. Необязательные поля, пропущенные в отчёте, сохраняют прежние значения. Для заполненного необязательного поля при принятии можно сохранить прежнее значение или применить предложенное. Новая карточка создаётся в статусе `ACTIVE`.

У обоих решений записываются UID администратора и серверное время проверки. Отклонение не меняет карточку данного ПК. Повторное решение по принятому или отклонённому отчёту запрещено. Отчёт с более ранним `submittedAt` не перезаписывает актуальную карточку. При одинаковом времени порядок определяется сравнением `reportId`.

Вне принятия администратор может изменить технические и учётные поля и статус с обновлением метаданных правки. Идентичность и ссылки на последний отчёт защищены правилами. Для ручной карточки используется ID с префиксом `manual-`, а связи с отчётом пусты. Окончательно удалить можно карточку, уже находящуюся в архиве. Входящие и обработанные отчёты сохраняются. При последующей реализации веб-интерфейс должен подтверждать изменения по той версии отчёта и карточки, которую администратор видел перед нажатием кнопки.

## Учётные записи для разработки

1. При локальной проверке тесты создают синтетические роли в эмуляторе. Сценарий входа создаёт отдельную временную учётную запись только в Auth Emulator. Нужны Node.js 24.15+ из ветки 24 и JDK 21+.
2. В разрешённом тестовом проекте уполномоченный администратор создаёт отдельные учётные записи Email/Password для сборщика, администратора и пользователя. По UID каждой записи администратор создаёт в Firestore документ `users/{uid}` с `role` и `enabled: true`. Проект и способ выдачи доступа согласуются до подключения клиента.
3. Для тестовой регистрации оператор использует временный пароль сборщика. Пароль администратора предназначен для его собственной сессии. Пароли и токены не включаются в EXE, Git и журналы.
4. При отзыве доступа уполномоченный администратор меняет `enabled` на `false`. Проверка в правилах блокирует запросы уже открытой сессии. Для остановки отправок всех сборщиков администратор выключает `acceptingReports`. В тестовом облачном проекте владелец также отзывает сессии учётной записи по процедуре Firebase Authentication.

Способ выдачи постоянного доступа Windows-агентам остаётся открытым. [Решения проекта](decisions.md)

## Проверка и ограничения

```powershell
npm --prefix tests/rules ci
npm --prefix tests/rules test
```

Проверены 19 сценариев в Firebase CLI 15.37.0 с Firestore Emulator 1.22.0. Они включают вход через Auth Emulator, потерю доступа после отключения роли, запреты при закрытом приёме и атомарное принятие. Среди отрицательных сценариев запись от USER, попытка удаления активной карточки, подмена UID и времени, изменение исходного отчёта, принятие без карточки, отдельная запись карточки, несовпадение полей, повторное и устаревшее принятие. Две параллельные попытки принять один отчёт завершаются одной успешной транзакцией.

Правила проверяют поля верхнего уровня, форму учётных данных, диапазоны, ограничение длины массивов и совпадение технических данных при принятии. Полную проверку содержимого массивов, согласованности производных значений и ограничений на размер отчёта и исправления выполняют валидаторы [контракта v1](DATA_MODEL.md). Фронтенд должен проверять полный контракт перед предложением принять отчёт. Фактическая достоверность оборудования подтверждается ручной проверкой.

Эмулятор проверяет правила и модель доступа. Проверка публичного TLS на Windows 7 SP1, разрешённый тестовый проект и согласование выдачи доступа остаются в [плане](IMPLEMENTATION_PLAN.md).
