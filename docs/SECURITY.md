# Firebase. Правила доступа и локальная проверка

Правила, Windows-агент и веб-интерфейс проверяются в локальных эмуляторах проекта `demo-pcinventory` на синтетических данных. CI запускает проверки правил и интеграционный тест Java-агента. Облачное развёртывание требует отдельного согласования.

## Роли и приём

| Роль | Разрешённые операции |
|---|---|
| `COLLECTOR` | Прочитать собственный документ роли и справочник `locations`. Создать `PENDING` в `inventoryReports/{reportId}`, пока открыт приём. |
| `ADMIN` | Читать реестр и входящие отчёты. Править, принимать и отклонять отчёты. Создавать, редактировать, архивировать и восстанавливать карточки, окончательно удалять карточки из архива. Управлять `settings/inventory.acceptingReports` и веб-учётными записями. |
| `USER` | Читать собственную роль, реестр ПК и справочник. Статистика и выгрузки строятся на основе чтения карточек. |
| Пользователь без активной роли | Прочитать собственный документ. При подтверждённой почте создать запрос на доступ. |

Любая операция над отчётом, карточкой или переключателем приёма проверяет `users/{uid}` и `enabled` при запросе. Изменение веб-ролей разрешено активному администратору с проверкой в правилах Firestore. Учётная запись сборщика создаёт отчёт с ID из пути, своим UID и серверным временем. В отчёте обязательны здание, этаж и кабинет. Отсутствующий документ настройки, выключенный приём и отключённая роль блокируют новые отправки. Возобновление приёма требует явного действия администратора.

## Исправление, принятие и отклонение

Администратор сохраняет исправления ожидающего отчёта в `correction` с техническими и учётными данными, UID и серверным временем. Оригинал отчёта сохраняется. Исправленная версия сохраняется перед решением о принятии. После обработки отчёт и его исправления защищены от правок.

Принятие одной транзакцией переводит отчёт из `PENDING` в `ACCEPTED` и создаёт или обновляет `computers/{deviceId}`. Правила сверяют оба документа до и после записи. Карточка получает технические данные и местоположение из сохранённого исправления или исходного отчёта с указанием ID и времени отправки. При обновлении сохраняется текущий статус карточки. Необязательные поля, пропущенные в отчёте, сохраняют прежние значения. Для заполненного необязательного поля при принятии можно сохранить прежнее значение или применить предложенное. Новая карточка создаётся в статусе `ACTIVE`.

У обоих решений записываются UID администратора и серверное время проверки. Отклонение не меняет карточку данного ПК. Повторное решение по принятому или отклонённому отчёту запрещено. Отчёт с более ранним `submittedAt` не перезаписывает актуальную карточку. При одинаковом времени порядок определяется сравнением `reportId`.

Вне принятия администратор может изменить технические и учётные поля и статус с обновлением метаданных правки. Идентичность и ссылки на последний отчёт защищены правилами. Для ручной карточки используется ID с префиксом `manual-`, а связи с отчётом пусты. Окончательно удалить можно карточку, уже находящуюся в архиве. Входящие и обработанные отчёты сохраняются. Веб-интерфейс подтверждает изменения по той версии отчёта и карточки, которую администратор видел перед нажатием кнопки.

## Учётные записи

После подтверждения почты пользователь создаёт собственный документ `users/{uid}` с ролью `USER`, `enabled: false` и `pending: true`. Правила сверяют адрес с Firebase Authentication. Запрос сам по себе не открывает доступ к реестру. Активный администратор одобряет его и назначает одну из веб-ролей. Сборщик управляется отдельно и недоступен в списке веб-учётных записей.

При деактивации запись Authentication сохраняется, а `enabled: false` отзывает доступ к данным в том числе для ранее выданного токена. Для правки ролей правила проверяют через `getAfter()`, что пользователь, указанный в `settings/access.adminUid`, остаётся активным администратором после транзакции. При деактивации или понижении указанного администратора ссылка переносится в той же транзакции. Проверка защищает прикладные роли Firestore. В пилотном проекте Firebase Authentication запрещает самостоятельное удаление учётной записи. Административные операции в Firebase Console регулируются правами проекта.

При регистрации и смене пароля веб-интерфейс требует 8–128 символов, строчную и прописную латинские буквы и цифру. Смена пароля требует повторного ввода текущего пароля, который проверяет Authentication. Принудительная политика для прямых запросов к API Authentication включается при подготовке облачного проекта.

Первый администратор и сборщик создаются при подготовке проекта. Для эмулятора используйте синтетические данные и отдельные временные учётные записи. Для сборки EXE согласованную учётную запись `COLLECTOR` передают через GitHub Secrets. Переключатель `acceptingReports` позволяет закрыть приём для всех сборщиков. [Локальный запуск](../README.md#локальный-firebase) · [Подготовка проекта Spark](FIREBASE_DEPLOYMENT.md)

В справочнике только здание, этаж и кабинет. Администраторская форма дополняет его в одной транзакции с принятием отчёта или сохранением карточки. [Решения проекта](decisions.md)

Переименование сохраняет идентификатор кабинета и обновляет публикуемые пути в `locations` одной транзакцией. Веб-интерфейс разрешает прежний путь из `locationRenames` в актуальное расположение. Сохранённые карточки и оригиналы отчётов сохраняют исходное название. Сборщик читает только актуальный справочник.

При удалении веб-интерфейс проверяет вложенные записи и связи с активными и архивными карточками. Транзакция проверяет версию справочника и карточек, чтобы при параллельном сохранении не удалить занятый адрес. Правила ограничивают записи в справочник активным администратором и требуют совместного изменения версии. Проверка количества связанных карточек выполняется в веб-интерфейсе. Для крупной ветки, превышающей размер одной транзакции, интерфейс завершает операцию без частичного переименования.

## Проверка и ограничения

```powershell
npm --prefix tests/rules ci
npm --prefix tests/rules test
```

Проверены 23 сценария в Firebase CLI 15.37.0. Они включают вход через Auth Emulator, подтверждение почты, одобрение доступа, защиту последнего администратора, изменения справочника, потерю доступа после отключения роли, запреты при закрытом приёме и атомарное принятие. Среди отрицательных сценариев запись от USER, попытка удаления активной карточки, подмена UID и времени, изменение исходного отчёта, принятие без карточки, отдельная запись карточки, несовпадение полей, повторное и устаревшее принятие. Две параллельные попытки принять один отчёт завершаются одной успешной транзакцией.

Правила проверяют поля верхнего уровня, форму учётных данных, диапазоны, ограничение длины массивов и совпадение технических данных при принятии. Полную проверку содержимого массивов, согласованности производных значений и ограничений на размер отчёта и исправления выполняют валидаторы [контракта v1](DATA_MODEL.md). Фронтенд должен проверять полный контракт перед предложением принять отчёт. Фактическая достоверность оборудования подтверждается ручной проверкой.

Эмулятор проверяет правила и модель доступа. Проверка публичного TLS на Windows 7 SP1 и разрешённый тестовый проект остаются в [плане](IMPLEMENTATION_PLAN.md).
