# Контракт данных v1

Две схемы Draft 2020-12 используют общие определения технических полей, учётных данных и форматов. Схемы загружаются из репозитория и входят в сборку агента.

| Документ | Схема | Синтетический пример |
|---|---|---|
| Входящий отчёт `inventoryReports/{reportId}` | [computer-report.schema.json](../contracts/computer-report.schema.json) | [На проверке](../contracts/fixtures/pending-report.json), [с частичными данными](../contracts/fixtures/partial-report.json), [принят](../contracts/fixtures/accepted-report.json) |
| Принятая карточка `computers/{deviceId}` | [computer-document.schema.json](../contracts/computer-document.schema.json) | [Карточка компьютера](../contracts/fixtures/computer.json) |
| Вложенные поля | [shared.schema.json](../contracts/shared.schema.json) | Поля используются в обоих документах |

## Приём отчёта

1. Агент создаёт `PENDING` с `reportId`, совпадающим с ID документа. При неопределённом результате отправки повтор использует тот же ID.
2. Администратор открывает отчёт, сверяет поля с текущей карточкой, если она существует, и вручную выбирает действие.
3. Принятие одной транзакцией создаёт или обновляет карточку по `deviceId` и меняет статус отчёта на `ACCEPTED`. Отклонение переводит отчёт в `REJECTED`. В обоих случаях записываются `reviewedAt` и `reviewedBy`. Исходные `hardware`, `assignment` и сведения об отправке сохраняются.
4. В карточке технические и учётные поля плоские. `lastReportId` и `lastInventoryAt` ссылаются на принятый отчёт и его `submittedAt`. `assignmentUpdatedAt` и `assignmentUpdatedBy` описывают учётные изменения. Новая карточка получает статус `ACTIVE`. При чтении прежней карточки отсутствие статуса трактуется как `ACTIVE`. Повторный отчёт сохраняет имеющийся статус.

Firestore хранит время как Timestamp. Для схемы и общих примеров значение проецируется в объект `{ "seconds": 1795600800, "nanoseconds": 123000000 }`. Сервер назначает время записи и время проверки. Совпадение ID документа с полем, права отправителя и администратора, серверное время, допустимость перехода и атомарность проверяются на этапе интеграции с Firestore.

## Поля и проверка

- Каждый модуль ОЗУ занимает отдельную запись в `ramSlots` со своей ёмкостью, типом, скоростью, производителем и другими характеристиками. `occupied` равен `true` для модуля, `false` для подтверждённого пустого места или `null` при неизвестном состоянии. Характеристики модуля заполнены только для `occupied: true`. `COMPLETE` требует известных состояний и уникальной пары «обозначение + банк» для каждой позиции. При `PARTIAL` подтверждённое количество свободных разъёмов может быть известно без их обозначений.
- `null` — неизвестное значение. Ёмкость хранится целыми байтами в точном диапазоне JavaScript. `ramTotalGiB` точно вычисляется делением `ramTotalBytes` на 1 073 741 824. `storageTotalBytes` вычисляется при известной ёмкости каждого найденного диска. `hasSsd` равен `true` при наличии проверенного SSD, `false` при известном типе всех найденных дисков без SSD, иначе `null`.
- `gpuModels` содержит уникальные известные модели в порядке их первого появления в `gpus`. `staticIpv4` содержит объединение адресов статических адаптеров. Режим `MIXED` требует одновременно подтверждённых DHCP и STATIC. Неопределённый адаптер учитывается в общем режиме при отсутствии подтверждённого `MIXED`.
- `floor` и `room` — обязательные непустые строки. Агент опускает пустые необязательные учётные поля. При принятии пропущенные поля сохраняют прежние значения, при создании карточки они записываются пустыми строками. Обязательность `building` зависит от решения по конфигурации организации.
- Схемы проверяют поля, типы, длины, перечисления, диапазоны и число элементов. Java и TypeScript дополнительно проверяют согласованность полей и лимит отчёта 64 КиБ. Java считает байты входящего JSON, TypeScript считает байты компактного JSON-представления полученного объекта.
- Перед отправкой агент проверяет доступность обязательных подсистем. Кодек работает со снимком данных. Состояние Windows-источников и причины полного сбоя определяются на стороне коллектора при подключении отправки.

## Коды предупреждений

| Группа | Коды |
|---|---|
| Система и CPU | `CPU_ATTRIBUTES_UNAVAILABLE`, `SYSTEM_ATTRIBUTES_UNAVAILABLE`, `OS_ATTRIBUTES_UNAVAILABLE` |
| Видеокарты | `GPU_ATTRIBUTES_UNAVAILABLE` |
| ОЗУ | `RAM_MODULES_UNAVAILABLE`, `RAM_CAPACITY_OS_VISIBLE`, `RAM_SLOT_TOPOLOGY_PARTIAL`, `RAM_SOURCE_CONFLICT`, `RAM_SPEED_UNAVAILABLE` |
| Диски | `DISK_ATTRIBUTES_UNAVAILABLE`, `DISK_TYPES_UNAVAILABLE` |
| Сеть | `NETWORK_MODE_UNAVAILABLE`, `NETWORK_ADAPTER_UNCLASSIFIED`, `STATIC_IPV4_UNAVAILABLE` |
| Идентификатор | `IDENTITY_PROFILE_FALLBACK` |

Коды фиксированы для версии 1. Русский текст предупреждения формируется при отображении. Реальные адреса, идентификаторы и учётные данные в примеры не входят.

## Проверка контракта

`mvn -B -f agent/pom.xml verify` проверяет схемы и обратную сериализацию DTO на Java 8. `npm --prefix web run test:contracts` проверяет типы и те же входные данные в TypeScript. CI запускает обе проверки.

На Windows прошли 38 проверок контракта в каждой реализации и девять проверок коллектора. Входящий отчёт и карточку также прочитали и повторно записали на Java 8 x86 из собранного EXE. Веб-сборка прошла после чистой установки зависимостей.
